# Dev Guidelines

A personal developer guidelines hub containing conventions, patterns, naming standards, and architectural decisions. This repository is the **single source of truth** for how code should be written, structured, and organized. Content lives in `docs/` and is published as a Docusaurus site.

> Any AI agent (GitHub Copilot, Cursor, opencode, etc.) working in projects associated with these guidelines **must** read and follow the conventions defined here before generating or modifying code. See `AGENTS.md` for repo-specific agent instructions.

Live site: `https://dev-guidelines-przk9sayy-abrmevals-projects.vercel.app`

## Overview

Guidelines are organized by **technology domain**. Each folder holds focused Markdown files for naming conventions, project structure, architectural decisions, and tooling choices. The same files are rendered as the public documentation site — no `/docs/` URL prefix (`routeBasePath: '/'`).

This repository exists to:

- Enforce **consistency** across all projects regardless of language, framework, or platform
- Give AI agents explicit context about personal conventions so generated code always matches expectations
- Reduce code review friction by having clear, documented standards
- Serve as onboarding material for any developer (or AI) joining a project

## Tech Stack and Tools

- **Framework:** Docusaurus 3.5+ (preset-classic, docs-only, blog disabled)
- **UI:** React 19, MDX, Infima + `src/css/custom.css` overrides
- **Language:** TypeScript 5.6
- **Package managers:** npm (CI) and Bun (local dev) — scripts work with both
- **Linting:** ESLint 9 + typescript-eslint + eslint-plugin-react
- **CI/CD:** GitHub Actions (`.github/workflows/deploy.yml`) → Vercel, on push to `main`

## Getting Started

### Prerequisites

- [Node.js >= 20](https://nodejs.org/)
- npm (comes with Node) or [Bun](https://bun.sh/)
- Git

### Installation Steps

1. Clone the repository:
   ```bash
   git clone https://github.com/abrmeval/dev-guidelines.git
   cd dev-guidelines
   ```
2. Install dependencies:
   ```bash
   npm ci
   ```
   ```bash
   bun install
   ```
3. Start the dev server:
   ```bash
   npm run start
   ```
   Open `http://localhost:3000` in your browser.

4. Verify before committing:
   ```bash
   npm run check
   ```

### Configuration Instructions

- `docusaurus.config.ts` — site title, URL, navbar, footer, Prism languages.
- `sidebars.ts` — manual sidebar tree. Add new top-level docs here, or use `_category_.json` for autogenerated sections.
- `src/css/custom.css` — theme overrides (Infima variables, markdown/table/blockquote styling).
- `eslint.config.mts` / `tsconfig.json` — lint and editor type support.

### Alternative Installation Methods

Run everything with Bun instead of npm (`bun run start`, `bun run build`, `bun run lint`, `bun run check`). CI always uses `npm ci`.

### Useful Commands

```bash
npm run start      # local dev server
npm run build      # production build
npm run serve      # serve the built site locally
npm run typecheck  # tsc --noEmit
npm run lint       # eslint .
npm run check      # typecheck + lint
npm run clear      # clear Docusaurus cache
npm run deploy     # manual deploy (CI normally handles this)
```

## Architecture Overview

Content-driven static site: Markdown in `docs/` → Docusaurus docs plugin → static HTML → Vercel. Navigation is defined in `sidebars.ts`; most sections also carry `_category_.json` files for labels and ordering. `onBrokenLinks` is set to `warn`, so broken links do not fail the build. CI runs `npm ci && npm run lint && npm run build` on every push to `main`, then deploys the prebuilt output to Vercel.

## How to Use This Repository

1. Before starting a new project, read the relevant section for your stack (e.g. `docs/Frontend/React/` for a React app, `docs/DotNET/VERTICALSLICE.md` for a .NET API).
2. Follow naming conventions from the matching `NAMING_CONVENTIONS.md`.
3. Follow the project structure from the matching `PROJECT_STRUCTURE.md`.
4. Follow Git conventions from `docs/Git/Commit.md` and `docs/Git/PR.md`.
5. Follow documentation requirements from `docs/Documentation/REQUIRED_DOCS.md`.

## Troubleshooting

- **Dev server port in use:** stop the other process on port `3000` or start with `npm run start -- --port 3001`.
- **Stale build output:** run `npm run clear` then `npm run build`.
- **Lint fails in CI:** run `npm run lint` locally; config files (`docusaurus.config.ts`, `sidebars.ts`) have relaxed rules, everything else follows the recommended TS + React sets.
- **Type errors in editor:** run `npm run typecheck`; `tsconfig.json` extends the Docusaurus base config and excludes build output.
- **Sidebar entry missing:** add the doc ID to `sidebars.ts` or check the folder's `_category_.json`.

## Contributing

These are personal conventions. To propose a change:

1. Use a feature branch — never commit directly to `main`.
2. Update the relevant `.md` file directly and keep it consistent with other files in the same domain.
3. Doc file names must be `UPPER_SNAKE_CASE.md`; headers use `##` / `###` with no level skipping.
4. End every guideline file with a `## References` section and `*Last Updated: DD Mon YYYY*`.
5. Do not add files that duplicate existing ones — check the folder first.
6. Use Conventional Commits (`feat:`, `fix:`, `docs:`, …) and PR titles like `PR: [Area] Description`.
7. Run `npm run check` and `npm run build` before opening a PR.
8. Follow `docs/Documentation/STRUCTURE.md` for README and doc structure.
